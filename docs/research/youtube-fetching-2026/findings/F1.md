# Angle: F1 — `feeds/videos.xml` channel feed: current reliability, 404/empty cases, why, workarounds

All live measurements taken 2026-09-27 from one workstation IP, Bun `fetch`, no cookies, no Google
account, no proxy. Server-reported time on the probe: `Sun, 27 Sep 2026 08:43:46 GMT`.

## Claims

### C1 — Feed is ALIVE in 2026-27, undocumented-but-still-current official reference exists
- The only official Google documentation of `https://www.youtube.com/feeds/videos.xml?channel_id=CHANNEL_ID`
  is the Data API v3 "Subscribe to Push Notifications" page, which uses that exact URL as the
  **PubSubHubbub topic URL** and shows the Atom payload (`<yt:videoId>`, `<yt:channelId>`, `<title>`,
  `<link>`, `<published>`, `<updated>`).
  — https://developers.google.com/youtube/v3/guides/push_notifications — fetched 2026-09-27 —
  confidence: **primary** (Google-owned, page footer "Last updated 2026-09-14 UTC").
  Exact quote: *"Set the **topic URL** to `https://www.youtube.com/feeds/videos.xml?channel_id=CHANNEL_ID`,
  where `CHANNEL_ID` is the YouTube channel ID for which you want to retrieve push notifications."*
- **No YouTube Help page documents the channel Atom feed.** Searched `site:support.google.com youtube rss
  feed atom channel` (native `web_search`, 2026-09-27). Every YouTube Help hit is about the *opposite*
  direction — YouTube Studio ingesting a creator's podcast RSS — or about channel URL formats
  (`support.google.com/youtube/answer/13973017`, `answer/6180214`). Confidence: **primary** (absence
  established by targeted search, not proof of non-existence).
- **Google has published NO statement of the 15-entry limit.** The push-notifications page says nothing
  about entry count, ordering, or which videos are eligible. The 15 cap is universally reported by
  implementations but is *not* a documented API guarantee. Confidence: **primary** for the absence.
- **No 2015 "Google Updates" announcement post for channel feeds exists** that I could find. I attempted
  `googleblog`/`developers.googleblog` "YouTube Atom feeds 2015 announcement" (native `web_search`,
  2026-09-27). The only first-party pages that actually publish feed URLs are ordinary dev-channel posts
  (e.g. https://developers.googleblog.com/en/expanding-our-developer-video-channel-lineup/,
  2015-09-03, which lists `UC_x5XG1OV2P6uZZ5FSM9Ttw` and also the legacy
  `?user=ChromeDevelopers` form). Confidence: **primary** that no announcement was found; **not
  established** that none exists.

### C2 — Live behaviour: 379/379 real channels returned HTTP 200. Zero 404s.
- Method: 379 unique `UC…` channel IDs collected 2026-09-27 from YouTube channel-filtered search
  (`/results?search_query=<q>&sp=EgIQAg%253D%253D`, 20 queries, `"channelId":"(UC[\w-]{22})"`),
  then each `https://www.youtube.com/feeds/videos.xml?channel_id=<id>` fetched once.
  Result tally: `{"200":379}` — 100% HTTP 200, **0 failures**.
  — measured 2026-09-27 — confidence: **primary** (own measurement, reproducible script).
- Of those 379: 373 returned exactly **15** entries; **6 returned fewer** (0, 5, 6, 10, 13, 14);
  **0 returned more than 15**. So the 15-entry ceiling is empirically exact and the only reason a
  channel returns fewer is that it has fewer than 15 public videos.
- Channel age is not a factor: the oldest in the sample is `UCOpNcN46UbXVtpKMrmU4Abg`,
  `<published>2013-12-15T20:44:04+00:00</published>`. New channels are not excluded.
  → **There is no creation-date cutoff.**

### C3 — ROOT CAUSE of the observed @Fireship 404: the channel-ID extractor, not the feed.
This is the single most important finding and it is fully reproducible.

- `/@handle` HTML contains **many** `UC…` strings, including decoys that do not correspond to any
  channel. Counts of distinct `UC[\w-]{22}` in `https://www.youtube.com/@Fireship` HTML (1,604,639
  bytes, HTTP 200), 2026-09-27:
  `UCsBjURrPoezykLs9EqgamOA` ×183 (the real one), `UC2Xd-TjJByJyK2w1zNwY0zQ` ×27 (**"Beyond
  Fireship" — a real different channel**), `UCEPBbIhMI5sPutK-OlwMVAl` ×6, `UCENTEDBgEIhMI5sPutK-Olw`
  ×6 (contains the literal string `ENTED`, clearly synthetic), `UCee3jrGUdb2ovrE7v4ncH3Q` ×3
  (**"Jeff Delaney"** — a real third channel), `UCEJSsCRgBIhMI5sPutK-Olw` ×3,
  `UCEI5iIhMI5sPutK-OlwMVAl` ×2, `UCEL3atEl8xaqYgFmC1gceyB` ×1, and more.
  Confidence: **primary** (own measurement).
- A naive extractor picks a decoy. Measured 2026-09-27, three handles:
  | handle | canonical | `/UC\w{22}/` first match | verdict |
  |---|---|---|---|
  | @Fireship | `UCsBjURrPoezykLs9EqgamOA` | `UCf2BtRM2dkgtbfo1eo89txe` (byte 716,658) | wrong → 404 |
  | @veritasium | `UCHnyfMqiRRG1u-2MsSQLbXA` | `UCpFa2Jx87f3DTViZQyK2V8i` (byte 736,745) | wrong → 404 |
  | @mkbhd | `UCBJycsmduvYEL83R_U4JriQ` | `UCQqDqARD22rye3xaPOGItim` (byte 731,133) | wrong → 404 |
  Confidence: **primary**.
- **The decoy IDs 404 on the feed** — `UCf2BtRM2dkgtbfo1eo89txe`, `UCpFa2Jx87f3DTViZQyK2V8i`,
  `UCQqDqARD22rye3xaPOGItim` each returned **HTTP 404, `content-type: text/html`, body = Google's
  generic `Error 404 (Not Found)!!1` page**, 2026-09-27. Confidence: **primary**.
- **The trap: the decoy channel *page* still returns HTTP 200.** `https://www.youtube.com/channel/UCf2BtRM2dkgtbfo1eo89txe`
  → 200, as do the other two decoys. YouTube serves a channel shell for any well-formed `UC`+22 string.
  So a "does the page load?" sanity check passes and the feed then 404s — exactly the reported symptom.
  Confidence: **primary**.
- **Extractors that work** (all verified 2026-09-27, all 3 handles):
  1. `<link rel="canonical" href="https://www.youtube.com/channel/UC…">` → correct on all 3.
  2. First `"externalId":"UC…"` / `"channelId":"UC…"` / `"browseId":"UC…"` match → correct on all 3.
  3. `og:url` = `https://www.youtube.com/channel/UC…` → correct.
  Confidence: **primary**.
- **Consequence:** the team's "some small channels return 404" is almost certainly *small/any channels
  whose page happened to yield a decoy to the regex*, cached for 24h by the current chain. It is not a
  feed outage and not a channel property. Fireship — a very active channel — has a working 200/15-entry
  feed right now.

### C4 — The 404 body is Google's generic error page, NOT a YouTube feed response
- Exact body of a 404 (2026-09-27, `content-type: text/html; charset=UTF-8`, 1,608–1,621 bytes
  depending on id length):
  ```
  <!DOCTYPE html><html lang=en><meta charset=utf-8>…
  <title>Error 404 (Not Found)!!1</title>
  …
  <p>The requested URL <code>/feeds/videos.xml?channel_id=UC…</code> was not found on this server. <ins>That’s all we know.</ins>
  ```
  Confidence: **primary** (own measurement; independently corroborated by user @RAWTEC pasting byte-identical
  markup in the Google AI Dev forum thread, 2025-12-28).
- **Design consequence: 404 is ambiguous.** It is returned identically for (a) a genuinely nonexistent
  channel id and (b) a valid id that YouTube is currently refusing. There is no distinguishing header
  or body. Verified that *every* malformed-id variant also returns the same page: wrong length
  (`UCsBjURrPoezykLs9EqgamO`, 24 chars), over-length, lowercase `uc…`, no `UC` prefix, `PL…`, empty
  string, `@Fireship` literal, and a URL-encoded injection — all 404, all `text/html`. 2026-09-27,
  confidence: **primary**.

### C5 — `?channel_id=` is byte-equivalent to the `UU` uploads playlist, and DOES include Shorts
- For Fireship, veritasium and the shorts-only @Shorts channel, the ordered `yt:videoId` list from
  `?channel_id=<id>` is **identical** to `?playlist_id=UU<id-without-UC>` (2026-09-27,
  confidence: **primary**).
- Feed `<title>` distinguishes them: `channel_id` form → channel's own name (e.g. `"Fireship"`,
  `"Veritasium"`); `UU` form → `"Uploads from Fireship"`.
- `UU` includes Shorts. Proof: for `UCHnyfMqiRRG1u-2MsSQLbXA` (veritasium), 11 of the 15 `UU` entries
  are absent from `UULF`; fetching those watch pages and reading `lengthSeconds` gives 66, 71, 77 s —
  Shorts. Confidence: **primary**.
- **Corollary that inverts the brief's premise:** the current chain's `?channel_id=` step *already*
  returns Shorts. The reference impl's `UC → UULF` "exclude-shorts" trick **loses** Shorts rather than
  fixing anything. `UULF` is the channel's `/videos` long-form tab (feed title `"Videos"`), not a
  repair for empty feeds. For Fireship `UULF` and `UU` are identical (0 diff); for shorts-heavy channels
  `UULF` silently backfills older long-form videos.
- `UULF` is also **not** an empty-feed fallback: the shorts-only @Shorts channel
  (`UCVFrJESKo4377DDTmYHJTrw`) returns **200 with 15 entries on all three forms**
  (`channel_id`, `UU`, `UULF`). Confidence: **primary**. The "UULF returns empty for many channels"
  comment in the reference impl was **not reproduced** on any channel tested.

### C6 — Shorts-only and live-only channels are NOT empty-feed cases
- Shorts-only `@Shorts` (`UCVFrJESKo4377DDTmYHJTrw`): `?channel_id=` → **200, 15 entries**, newest
  2026-09. `UU` → 200/15. `UULF` → 200/15. 2026-09-27, confidence: **primary**.
  → the "shorts-only channels get an empty feed" hypothesis is **falsified** for this channel.
- Live-only channels: 8 of 8 sampled 24/7 live channels returned **200 with 15 entries**
  (`UCvi6hEzLM-Z_unKPSuuzKvg` "ANC 24/7" oldest entry `2026-09-27T01:00:28+00:00` — i.e. finished
  streams land in the feed the same day). 2026-09-27, confidence: **primary**.

### C7 — HTTP 200 + 0 `<entry>` is a legitimate, common state — and it is the real "empty widget" case
- `UCOpNcN46UbXVtpKMrmU4Abg` ("Gaming", created 2013-12-15): **HTTP 200**, well-formed Atom,
  **zero `<entry>` elements**. Body has full `<feed>`, `<id>`, `<yt:channelId>`, `<title>Gaming</title>`,
  `<published>2013-12-15T20:44:04+00:00</published>` and simply no entries. 2026-09-27,
  confidence: **primary**.
- **Music/Topic (brand) channels are the highest-yield empty case.** Of 20 `"- Topic"` channels sampled
  2026-09-27: **2 returned 200 with 0 entries** (`UCCqjAiTi43MnqoBZ9S_xTgw` "PURPOSE OFFICIAL AUDIO -
  Topic", `UCtHDnWNV8o2IBEBAsCZYZ5A` "NEHEMIAH PURPOSE OFFICIAL AUDIO - Topic"), 1 returned 1 entry,
  1 returned 2 entries, 16 returned 15. ≈10% empty, 15% partial. Confidence: **primary**.
- Verified these are genuinely empty, not a fetch failure: fetching
  `https://www.youtube.com/channel/<id>/videos` for both 0-entry Topic channels returned **HTTP 200**
  with `0 × videoRenderer`, `0 × richItemRenderer`, and no `videoCountText`. 2026-09-27,
  confidence: **primary**.
- **So the only two feed outcomes are: 404 = wrong/nonexistent ID; 200-with-0-entries = channel has
  no publicly-listed videos.** There is no third "empty because broken" state observed.

### C8 — Serving contract: what YouTube tells you to cache
- Response headers on a healthy feed, 2026-09-27 08:43:46 GMT, confidence: **primary**:
  ```
  server: YouTube RSS Feeds server
  cache-control: public, max-age=900          <-- 15 minutes
  content-type: text/xml; charset=UTF-8
  content-encoding: gzip
  age: 18
  expires: Sun, 27 Sep 2026 08:58:46 GMT
  x-frame-options: SAMEORIGIN
  ```
  Note `server: YouTube RSS Feeds server` is present on 200s and **absent on 404s** (404s carry no
  `server` header in my captures) — the cheapest available positive/negative discriminator.
- **No `ETag` and no `Last-Modified` is sent.** Sending `If-None-Match` with the (absent) ETag returned
  **200, not 304** — there is no conditional-request support. 2026-09-27, confidence: **primary**.
  → Polling more often than every 15 min cannot be made cheaper; it can only be more expensive.

### C9 — User-Agent is irrelevant. Bot-detection is NOT the 404 cause.
- `?channel_id=UCsBjURrPoezykLs9EqgamOA` under four UAs, 2026-09-27 — **all HTTP 200, all 22,083
  bytes, identical**: desktop Chrome UA, no `User-Agent` header at all, `curl/8.0`, plain
  `Mozilla/5.0`. Confidence: **primary**. So the "plain Mozilla UA" choice in the current chain is
  neither helping nor hurting.
- `&hl=en` changes nothing: `?channel_id=…&hl=en` gave the same 200 and 15 entries as without it
  (byte delta is only the `hl` echo, +10 bytes). Confidence: **primary**. **`hl` is not a workaround.**

### C10 — Rate limiting did NOT reproduce. 80/80 rapid requests = 200.
- 80 sequential feed requests across 8 rotating channel IDs with zero delay, desktop Chrome UA,
  2026-09-27: `{"200 YouTube RSS Feeds server": 80}`, first non-200 `null`, and an immediate
  follow-up request also 200. Confidence: **primary**.
- → **Simple request-rate throttling from a single IP is falsified** as the cause of the reported 404s.
  Whatever the real mechanism is, it is not "too many requests, too fast" in a short window.

### C12 — Can a channel that HAS a feed LOSE it? No evidence of permanent loss; evidence only of transient loss.
- 379/379 long-established channels still had feeds on 2026-09-27, including one created 2013
  (C2). Nothing in the tracked issue trackers describes a channel permanently losing its Atom feed.
- Miniflux #4261 explicitly says the opposite of permanent: *"Manually refreshing the feed(s) … works
  just fine"* and the label is `third-party to resolve`.
- The only permanent-loss path I found is **channel termination**, and the evidence is about yt-dlp,
  not the feed: **Youtarr #621** "handle terminated YouTube channels gracefully", opened **2026-05-16**,
  closed as `enhancement` — https://github.com/DialmasterOrg/Youtarr/issues/621 — fetched 2026-09-27 —
  confidence: **primary**. Verbatim: *"When a subscribed channel is terminated by YouTube, yt-dlp errors
  with: `YouTube said: This account has been terminated for violating Google's Terms of Service.`"*
  This establishes that terminated channels produce a **distinct, recognisable error**, which is the
  right model to copy: recognise terminal states explicitly rather than letting them look like 404s.
  **It does not tell us what the Atom feed returns for a terminated channel** → see Gaps.

## Conflicting evidence

1. **"Shorts-only channels get an empty feed"** (stated in the brief as a known case) vs **my C6
   measurement**. The shorts-only `@Shorts` channel returns 200/15 on all three forms.
   Reconciliation: the premise is not reproducible on the one shorts-only channel I could locate; and
   C5 shows `UULF` is the long-form tab, so *using* UULF on a shorts-heavy channel is what produces
   the shorts-omitted appearance. The brief's claim may be a misattribution of the UULF behaviour.
   Carried forward: shorts-only channels have working feeds (confidence high, n=1 channel).
2. **"UULF returns empty for many channels"** (reference-impl comment) vs **C5**: zero cases
   reproduced in 8 channels × 3 forms. Reconciliation: unreproduced; likely historical or specific to
   a client that also depends on the `/videos` tab HTML. Carried forward as *not reproducible today*.
3. **"Rate limiting"** (implied by HackerX's *"defense mechanism of the feeds against bots or ai"*)
   vs **C10**: 80 rapid requests all 200. Reconciliation: the real signal is not throughput —
   Miniflux and the forum both report *same URL works via curl/browser but 404s from the app's
   fetcher*, and HackerX correlates it with **client uptime** (12h+), not request count. That points at
   long-lived-connection / client-fingerprint / per-source reputation, not a request quota.
   **I could not reproduce it and no source names a mechanism — the cause remains unverified.**
4. **"404 = channel has no feed"** vs **C3/C4**: 404 is produced by malformed *and* decoy IDs. A 404
   carries no information about the channel. Carried forward: 404 is never diagnostic.
5. **`?user=<legacy username>`** returns **HTTP 200** but for the **wrong channel**.
   `?user=MrBeast&feature=rss` → 200, 3 entries, `yt:channelId` = `goFStVyEsm8tBZP5NC-aBQ`, title
   `"MrBeast"`, videos from 2006–2007 with 11K–34K views, in a **legacy feed format**
   (`v/<id>?version=3` Flash content, `media:community` star ratings, no `media:group`).
   The real MrBeast (`UCX6OQ3DkcsbYNE6H8uQQuVA`) is 200/15 with modern format and
   `v9QtM6qnG50,T_SMf9j50uc,gTKS8SAwUzE`. Same title, different channel — a legacy-username squatter.
   2026-09-27, confidence: **primary**. **`user=` is a correctness trap; never use it.**

## Gaps

- **The mechanism behind the intermittent 404 bursts (C11) is undocumented and unreproduced.** No Google
  statement exists, no issue tracker diagnosis exists, and 80/80 rapid requests did not trigger it.
  I could not obtain a second egress IP to test whether it is per-IP. **Unverified.**
- **The YouTube Help community thread on the 404/500 returns 410 Gone** (C11). I never saw its contents,
  so I cannot say whether a Google employee ever responded there. Someone with an archive or an
  authenticated session would need to retrieve it.
- **Feed behaviour for a terminated channel is unknown.** Youtarr #621 documents the yt-dlp message,
  not the Atom feed. Does it 404, or return 200/0 entries? Unverified — and it matters for the
  loud-failure policy, because "terminated" and "no public videos" may be indistinguishable.
- **Whether premieres (scheduled/upcoming) and currently-running live streams ever appear in the feed**
  is only half-answered: completed streams do (C6). A channel whose *only* content is an in-progress
  premiere was not observed. Unverified.
- **Non-15 counts in the 379 sweep (6 channels) were not individually explained** beyond "fewer than
  15 public videos" — I confirmed one (0-entry) but did not enumerate the other five.
- **No primary source was found for the 15-entry limit as an intentional design decision.** It is
  empirically exact (C2) but Google has never published it. Any claim that it is contractual is
  unsourced.
- **No Google Updates / Google Developers Blog post announcing per-channel feeds was found.** The feed
  may have simply existed before those blogs covered it.
