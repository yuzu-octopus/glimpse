**EXECUTED VERIFICATION (my own runs, 2026-09-27, this machine, Bun 1.4.2, no cookies / no account / no PO token / no proxy):**

- `Innertube.create().getChannel('https://www.youtube.com/@Fireship/videos')` on `youtubei.js@18.1.0` →
  `InnertubeError: Request to https://www.youtube.com/youtubei/v1/browse?prettyPrint=false&alt=json failed with status code 400`
  (server body: `{"error":{"code":400,"message":"Request contains an invalid argument.","status":"INVALID_ARGUMENT"}}`). — `primary` (own execution)
- **Root cause is in the library's own source, not YouTube blocking us.** `src/Innertube.ts:385-395`:
  ```ts
  async getChannel(id: string): Promise<Channel> {
    throwIfMissing({ id });
    const browse_endpoint = new NavigationEndpoint({ browseEndpoint: { browseId: id } });
    let response = await browse_endpoint.call<IBrowseResponse>(this.#session.actions, { parse: true });
  ```
  It passes the raw handle/URL string straight through as `browseId`. It never calls `/navigation/resolve_url` — even though `resolveURL()` exists at `src/Innertube.ts:479` and is public. — `primary`
- **Fix proven to work:** `await it.resolveURL('https://www.youtube.com/@Fireship/videos')` returned HTTP 200 with
  `{"browseId":"UCsBjURrPoezykLs9EqgamOA","params":"EgZ2aWRlb3O4AQCSAwDyBgQKAjoA"}`, and `ep.call(actions,{parse:true})` returned HTTP 200. — `primary` (own execution)
- **Hand-rolled control:** POSTing `browseId:'@Fireship/videos'` straight to `/browse` returns **400** for **all 8** client/version combinations tried (WEB `2.20260623.01.00`, `2.20260708.00.00`, `2.20260915.00.00`; MWEB; ANDROID `21.26.364`; IOS `21.26.4`; TVHTML5 `7.20260707.07.00`; WEB_EMBEDDED_PLAYER), with and without `?key=`, on both `www.youtube.com` and `youtubei.googleapis.com`. Adding the resolve step first makes `/browse` return **200 with 30 `videoId`s and 5–6 continuation tokens**. **Conclusion: raw `browseId` guessing is dead; `navigation/resolve_url` is the mandatory first hop.** — `primary` (own execution)
- **Second, independent defect in v18.1.0:** via the working `resolveURL` path, `Channel.videos` returns **30 items** whose class is **`LockupView`**, with keys `['type','content_image','metadata','content_id','content_type','renderer_context']`. `item.id`, `item.title`, `item.published_time_text`, `item.view_count` are all **`undefined`** (verified on both `@Fireship/videos` and `@veritasium/videos`). Data is present but under `content_id` / `metadata` / `content_image`, i.e. YouTube's new lockup layout is not mapped to the ergonomic accessors. — `primary` (own execution)
- Open issues: **88** as of 2026-09-27, newest 2026-09-25. A matching 400-on-`getX` issue exists and is **still open since 2025-03-08**: **#916** *"Getting 400 BadRequest 'Request contains an invalid argument' from almost every getX method"* (reported on v13.1.0, logged at `youtubei.js/src/core/Actions.ts:166`). — https://github.com/LuanRT/YouTube.js/issues/916 — `primary`

## 10. INCIDENTAL but load-bearing: our handle→channelId regex is silently wrong

Found while verifying §5. Not my angle, but it is a live correctness bug in the chain being
researched, and it is a better explanation for "some channels return nothing" than a 404.
Verified by execution, 2026-09-27, `GET https://www.youtube.com/@<handle>` with a plain Chrome UA:

| handle | first `"channelId":"UC…"` in HTML | `<link rel=canonical>` / `og:url` | distinct UC ids on page | RSS of the *wrong* id |
|---|---|---|---|---|
| `@Fireship` | `UC2Xd-TjJByJyK2w1zNwY0zQ` | `UCsBjURrPoezykLs9EqgamOA` | 3 | 200, 15 entries, author **"Beyond Fireship"** |
| `@veritasium` | `UCin0m13qWv3-051xlWlHamA` | `UCHnyfMqiRRG1u-2MsSQLbXA` | 13 | 200, 15 entries, author **"Veritasium en Français"** |

- `navigation/resolve_url` agrees with the canonical/`og:url` id on all three handles, and
  disagrees with the first-in-page regex on all three. — `primary` (own execution)
