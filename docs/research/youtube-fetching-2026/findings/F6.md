→ **Conclusion: whatever broke in Dec 2025 – Feb 2026 is currently NOT broken.** The failures

**This is the single most important corrective to the "YouTube removed the RSS feed" narrative
that dominated the issue threads of that period.**

### F. Documentation status — the feed has no user-facing support commitment

- **Google's developer docs still name it.** `developers.google.com/youtube/v3/guides/push_notifications`
  — page footer reads **"Last updated 2026-09-14 UTC"** (13 days ago) — instructs you to set
  the PubSubHubbub **topic URL** to
  `https://www.youtube.com/feeds/videos.xml?channel_id=CHANNEL_ID` and shows the Atom payload
  with `<yt:videoId>` / `<yt:channelId>`. — fetched 2026-09-27 — **primary**
  → two consequences: (1) the `channel_id=` feed is referenced in current first-party docs,
  which is a (weak) support signal; (2) **PubSubHubbub push is an officially documented
  alternative to polling** — but it needs a publicly reachable HTTPS callback, which a
  LAN-only dashboard does not have.

- **YouTube Help no longer mentions it at all.** `support.google.com/youtube/answer/6098135`
  — the page that historically hosted the "RSS Reader / export subscriptions to OPML"
  section — **now resolves to "Where you can't watch: Unsupported device models YouTube apps -
  Android"**. No RSS/OPML content. — fetched 2026-09-27 — **primary**
  → the endpoint survives in *developer* docs and is **absent from *user* help**. Zero support
  commitment, zero SLA. Any dashboard depending on it is riding an unbacked surface.

- **The HTML fallback did not rescue anyone in this window.** In none of the 2025-12 →
  2026-05 threads did a reporter report that scraping `/@handle/videos` or any youtube.com
  HTML worked while `videos.xml` failed. Where users hand-checked the feed URL they saw the
  same 404 (Gr0bGr0b, 2026-09-10), and where they hand-checked the *page* the page was fine
  while the feed was not (lentscode, 2025-12-30; sethCodesSometimes, 2026-02-14).
  → **The two youtube.com surfaces fail independently.** A working `ytInitialData` page
  is therefore a genuinely useful *second* path, not a redundant one — but it is not a proven
  rescue for a feed outage. No source in this angle tests it. **Unverified either way.**

## Conflicting evidence

- **"YouTube removed the RSS feeds" vs "it's intermittent."** Several 2025-12/2026-01
  reporters concluded removal (jaynemo: *"it looks like the scum have removed the
  …endpoint"*; aho15 on glance #933: *"the used endpoint to get videos has been removed"*).
  **Resolution — the intermittent reading wins, on two independent grounds:** (1) every one of
  those same URLs returned HTTP 200 with 15 entries when I re-tested them on 2026-09-27, 12/12
  consecutive times; (2) the same threads document spontaneous recovery without any code change
  ("works again???? somehow???", "got resolved on it's own", "but now is back up"). Removal
  claims were snapshots of an outage.
- **"It's anti-scraping" vs "it's a YouTube bug."** The forum OP asked whether it was a rate
  limit and got no Google answer. @HawkX's uptime correlation and the FreeTube 403 +
  "automated queries" body support anti-abuse; the moving failure window and the HN "works fine
  for me" reports support edge/load-dependent degradation. **Resolution: treat anti-abuse as
  the most probable mechanism, explicitly labelled inference** — Google's own tracker text
  ("if it's the anti abuse mechanism that prevented the call to happen") is the only first-party
  statement, and I could not open the ticket. Nobody has a confirmed root cause.
- **404 rate-limit cadence: "a few times each year" vs "daily".** FreeTube's maintainer says
  a few times/year (2025-12-20); efb4f5ff says "daily" (2025-12-26); the forum OP says the
  problem recurred Jan 10, Jan 21, Feb 5, Feb 22, Apr 27, Apr 29, May 2. **Resolution:** not
  contradictory — "a few times each year" refers to *full outages*; the forum reports are
  *partial/short 404 windows*. The dashboard-relevant unit is the short window, not the outage.
- **Are `channel_id` and `UULF` equally affected?** FreeTube/jaynemo saw 404 on `channel_id`;
  ocaml.org saw both; Glance only ever hit `UULF` because that is its default. **Gap:** I
  could not find a source measuring the two paths' failure rates side by side during one
  outage. Our chain's primary path (`channel_id=`) is *not* the path all the Glance reports
  exercise.

## Gaps

1. **Could not verify Google's issue tracker 322736318 / 429563457** — `issuetracker.google.com`
   requires sign-in. The "Won't Fix (Infeasile) / anti abuse mechanism" quote is therefore
   **secondhand via HN**, not primary-verified by me.
2. **Could not open any Reddit thread.** Network-policy block on every route tried. The two
   Reddit leads (`r/rss/1t5ga95` "YouTube's RSS feeds are completely broken";
   `r/youtube/1r61jpo` "All YouTube channel RSS feeds are down, return 404", snippet *"Since
   early December 2025… it always happens within a specific three-hour window"*) exist only as
   search-engine snippets. **Their dates are unverified — do not cite them as dated evidence.**
3. **No datacenter-IP test.** I am on a residential connection. Claims that datacenter IPs are
   specifically blocked rest on commercial scraper blogs (secondary, partly vendor-marketing)
   and on yt-dlp's IP-ban reports, **not** on anything I reproduced. The 403 + "automated
   queries" body in FreeTube #8443 is from a **residential, non-VPN** user, which shows the
   block is not datacenter-exclusive. **Our exact deployment (no browser, no account, no
   proxy) is unverified against YouTube's bot defences.**
4. **No consent-interstitial evidence either way.** My probe found no interstitial from this
   IP/geography, so the EU-DSA consent wall is **not** an observed problem for us today — but
   I tested one location only, so this is not a general clearance.
5. **No official Google changelog, postmortem, or acknowledgment** for the Dec 2025 – May 2026
   RSS degradation exists in any source I could reach. The only first-party trace is the
   anti-abuse/won't-fix tracker text (unverified).
6. **The exact window mechanism is unknown.** Reported windows conflict (09:00–12:00 UTC vs
   ~19:00–20:00 UTC vs "end of each day after 12h uptime"), which rules out a simple fixed
   schedule and points at load/edge state. I could not determine whether a *specific* edge or
   region is degraded, so I cannot tell you whether retrying from a different vantage point
   would help.
7. **Playlist feeds were not separately stress-tested during an active outage** — the only
   playlist data point is ocaml.org's, where 6 of 9 failing sources were `playlist_id=` feeds
   (and those were ordinary user playlists, not UULF).
